# S-PRES — GRAPH VISUALIZATION SPEC (addendum-4 upgrade 5, named design task)

Source of truth: docs/rde_nozzle_pipeline_decision_map.md (refereed,
0 BREAK / 0 REPAIR; 8 stages, 79 nodes = 62 ledger C1..C62 + 17
non-ledger, 45 edge entries incl. 1 declared anti-edge E34).
Binding rule (addendum 3(B)): the deck presents THE map, made visual
and walkable — not a summary of it. 62 nodes NEVER on one slide.

## LAYER MODEL (3 layers, per-layer legibility checked by comms refuter)

L0 — OVERVIEW (1 slide): the 8 stages as a left-to-right pipeline
  ribbon (Stage 1 DATA CONTRACT -> 2 REPRESENTATION -> 3 MARCH &
  UNIT PROCESSES -> 4 CERTIFICATES -> 5 ESTIMATOR & BANDS ->
  6 OPTIMIZER & ENGINE -> 7 AGGREGATION & FRONTIER -> 8 VERDICT &
  CLAIMS). Each stage box: name + node count + a status mini-bar
  (stacked: DECIDED green / MIXED amber / NEVER open-circle grey /
  SA outlined). The 4 cluster surfaces drawn as labeled arcs OVER
  the ribbon: A engine cluster (stage 6 <-> 4), B contract (stage 1),
  C ship-gate (stage 7), D external-expansion Veen->C61->ADR-D4
  (stage 8). One takeaway line: "62 scelte, ognuna a registro con
  alternative + falsificatore; 12 DECIDED / 36 MIXED / 12 NEVER /
  2 SINGLE-AUTHOR — dichiarate, non nascoste."

L1 — STAGE ZOOM (2-3 slides in main deck, all 8 in backup): one
  stage per slide. Nodes as cards: id + 3-5-word choice + status
  glyph. Edges INSIDE the stage drawn; edges leaving the stage =
  stub arrows with the target stage number. Zooms selected for the
  main deck: Stage 6 (optimizer/engine — the F2-entry cluster
  surface A story), Stage 7 (forchetta/ship-gate — the honesty
  story), Stage 3 or 5 on time budget. Remaining stages -> backup
  deck, one slide each, same template (the walkable graph promise).

L2 — NODE CARD (backup deck, on-demand): per selected load-bearing
  node: choice of record / alternatives weighed / why / falsifier +
  status / open duty + owner window. Populated verbatim-compressed
  from the map row (cite-only; the map cell's citation is the
  card's citation). Cards prepared for the Q&A-mapped nodes (the
  red-team map names which).

## VISUAL STATUS ENCODING (uniform across layers)

- DECIDED: filled green square
- MIXED: half-filled amber square (decided branch + open sibling)
- NEVER: open grey circle + owner-window tag (all 12 carry
  owner+trigger of record — the encoding must SHOW the owner, that
  is the honesty content)
- SINGLE-AUTHOR: outlined violet diamond (2: C17, C18)
- non-ledger ⊘ nodes: rounded rectangle, status verbatim from source
  (LANDED / ARMED GATE / USER-PENDING / F2-QUEUED / OPEN)
- anti-edge E34: dashed grey with an X glyph, footnoted (recorded so
  the non-edge is not mistaken for an omission — say this out loud,
  it is a rigor exhibit)

## RENDER MECHANISM

Programmatic (deck-as-code, pipeline vehicle): matplotlib layout
generated by a script in the build pipeline (same provenance
discipline as every figure: script + JSON node/edge list committed;
the node/edge list EXTRACTED from the map file, never hand-typed —
extraction script asserts counts 62/17/45 against the map's machine
summary, so a map edit breaks the build, not the slide truth).

## COMMS-REFUTER CHECKS (per-layer, Block 2)

- L0: readable at 3 m / 1080p projection; stage names >= 20 pt
  equivalent; status bars decodable without the legend after slide 1.
- L1: <= 12 node cards per slide (Stage 6 has 20 ledger nodes ->
  split into 2 panels: engine-core vs design-basis C1-C8); id + gloss
  legible; edge stubs labeled.
- L2: one node per card region, verbatim-compressed <= 40 words per
  field.
- Color-blind safe pairing: green/amber/grey/violet distinguished by
  SHAPE as well as color (square/half/circle/diamond).
